# Testing labels — one evidence decision, local exclusions first

This contract consolidates the existing TESTED format with `_decision-evidence.md`. It overrides older instructions that license testing from page type, a blanket owner statement, copied category methods, or `--tested yes` alone. Preserve the existing tested title, byline, three method bullets and pick layout when the page qualifies and the work supports them.

Read `_testing-labels.local.md` when present for the installed site adapter and content-snapshot shape. Local instructions may add stricter exclusions but cannot weaken evidence review. Keep this local adapter note separate so shared-rule syncs never overwrite it.

## Fleet rules

1. Discover the ACTIVE site's `_experience.md`, local content standard, topic/page exclusions, template switch and review/schema rules. Never copy Layer3's permissions, author, methods, exclusions-as-an-allowlist, or test records into another site. No local permission (including no section G) means no TESTED format. An adapter or policy file must never create permission.
2. Apply existing exclusions FIRST. Medical/psychedelic treatments, clinical outcomes, medicines, supplements' health effects, clinics, legal/financial/professional services and other locally excluded topics stay excluded even when a packet exists. Preserve stricter local rules and page-type exclusions for pricing, explainers, how-to, tools and news. Independent editorial/medical review is distinct from product testing. Published clinical research is reported evidence, never our clinical testing. Modeling cannot establish treatment safety or efficacy.
3. Then classify the ACTUAL work: `tested`, `calculated`, `modeled`, `client-record`, `reported`, or `unknown`. Only relevant executed product tests with full item coverage can enable the page-wide TESTED presentation. Partial tests cannot enable “we tested every item” or a page-wide tested badge. A scoped first-person test statement requires a separate supported, audited scope mechanism in the local adapter. The current Layer3 adapter supports only complete page-wide test coverage, so partial-testing drafts must narrow to a fully supported scope and re-audit, or omit the unsupported testing format/claims. Do not imply that a partial claim is supported by the current page-wide check. Analysis/modeling uses the specific visible attribution in `_decision-evidence.md`; it never enables testing schema, title, byline or method headings.
4. Preserve the old format for an approved tested page. The three method bullets must describe the actual recorded work for EVERY ranked item. Category sets are reusable wording only when all three are true; adapt inaccurate bullets through the writer instead of copying them blindly. Detailed supported measurements may appear in the findings. Do not automatically repeat a testing cue where the existing tee-up already says what we did.
5. A displayed testing year comes from the executed runs, not today's calendar or the article's update date. For multiple included years, use the oldest year unless the page explicitly reports scoped dates. Never turn a 2025 test into “Tested 2026” by rebuilding.

## Phase 0 / Phase 3 / Phase 4 integration

- Phase 0 records local permissions, exclusions and the label adapter. No testing permission is the normal disabled branch; do not add section G to make a page qualify. Missing adapters must be wired and verified before a tested page can ship; source-only/excluded pages need no new testing UI.
- Phase 3 records the local eligibility decision separately from evidence. `eligible: true` is permission to CONSIDER the format, not a claim that a test happened. Assemble real run records first. A qualifying draft with complete relevant runs may use `--tested yes` to get the existing layout; the draft is not approved or publishable yet. Otherwise use `--tested no` and accurate analysis/modeling/reporting language. Give the writer the approved facts and methods. Do not invent records to preserve a previous badge.
- Phase 4 independently checks the exact final content, methods, item coverage, provenance wording, local exclusions and raw records. On PASS, record a per-route approval bound to the final content hash and hashes of the run/review artifacts. The reviewer must differ from the creator. A content or evidence change invalidates the approval; re-audit before restoring the tested label. No new human gate is added.
- The page template, title, byline, method section, pick presentation and testing-related schema must use the SAME evidence decision. The writer flag and `howWeTested` field are not independent switches. Preserve ordinary article/reviewer schema and excluded-site reviewer requirements.
- Before publication, run the adapter's check on the actual normalized page and inspect the built HTML, including metadata and schema. Residual unsupported “we tested” prose/meta is a failure even when the badge is off; repair through the normal writer/review path. Do not silently bulk-rewrite historical articles or mark unknown legacy claims as verified. List unresolved legacy pages separately and block their publication when touched.

## Layer3 adapter (implementation example, not a fleet path assumption)

- `scripts/tested/check.mts`: takes candidate `route`, `content` (the exact normalized object passed to the template), section/slug/text fields; returns separate `eligible`, `tested` and `reason`. The live templates use the same decision in `src/utils/testedPage.ts`.
- `.claude/testing-policy.json`: `schemaVersion: 1`, `allowTestedLabels`, and `experience: {path, sha256}` referencing this site's own permission file. Changing permission requires revalidating this policy; no implicit permission fallback.
- `data/testing-evidence.json`: `schemaVersion: 1`, `pages` keyed by canonical route. Empty registry is deliberately unverified, not a claim that no historical testing occurred.
- A page entry has `basis`, `createdBy`, `contentSha256`, unique `items`, `runs` and `review`. Each run has `items`, real `testedAt` (`YYYY-MM-DD`) and `artifact: {path, sha256}`. Review has `status: "pass"`, a distinct `reviewer`, `coverage: "all-ranked-items"`, the same `contentSha256`, `evidenceSha256` (the canonical hash of `{basis, createdBy, items, runs}`), and `artifact: {path, sha256}`. That artifact is an independent JSON decision containing the same status, reviewer, coverage, content hash and evidence hash; a narrative audit may be linked from it. Changing any included run, test date, item or file hash requires a fresh independent decision. Artifacts are project-relative and private; they must exist unchanged in the build checkout. The review verifies that the item list really matches the page; a hash cannot establish truth by itself.
- Use `scripts/tested/register.mts <approval.json> <normalized-page.json>` after the independent PASS to install/replace one route's record. It validates the candidate, policy, artifact hashes and local exclusions before writing. No boolean-only attestation or automatic grandfathering.
- Calculated/modeled/reported evidence stays in the regular run packet; it requires no fake tested approval. The template stays on its ordinary presentation, with any helpful analysis attribution in the page body.

Portable implementations may use another storage format, language or framework, but must preserve these same decisions and stale-evidence checks. Do not transplant Layer3's TypeScript adapter into an incompatible site or change a site's exclusions to make the adapter pass.
