# /tool-usage-mindmap-auto — used tools → better tools + the next tools

> **‼️ AUTONOMOUS.** No human checkpoint. Never print "Approve?". **Every run ends with an owner email (USER RULE 2026-10-11)** — shipped, nothing to work, or failed (STEP 8).
> Run `.claude/scripts/deploy-run-to-main.sh mark` FIRST, before any commit.

**Inputs from the routine prompt:** `TOOL_SITE` (the bare domain as tracked, e.g. `chalkbox.org`) and `BASE_URL` (the host that answers 200, e.g. `https://chalkbox.org`).

**The whole idea:** people used these tools. Be that person, find what got in their way, fix it, then build the tool they'd reach for next. This is a thin wrapper around the mindmap engine — mindmap does validation, dedup, writing, audit, linking, sitemap, IndexNow, deploy and live verification. This file only adds the persona work, the `tool fix` rows, and a 3-new-tools-per-run cap; mindmap itself builds tool rows (Phase 3c).

## ‼️ NO SHORTCUTS — enforced by hooks, not by trust (USER RULE 2026-10-11)
The 2026-10-11 pilot edited tools before walking them, never saved a mindmap chart, skipped mindmap phases 0/1/2/5/6/8 and still shipped. So every stage now ends with a gate command, and `.claude/tools/tool-usage-gates.sh` (PreToolUse hook) **blocks** the next stage until that gate has passed:

| Gate (`python3 scripts/tool_usage/tool_usage_gate.py …`) | Run it after | It requires | Unlocks |
|---|---|---|---|
| `start --site "$TOOL_SITE" --base-url "$BASE_URL"` | STEP 1 found work | — | the run (until then every edit, deploy and email is blocked on this branch) |
| `persona` | STEP 3 | `picked.json`; per tool `personas/<tool>.md` (Evidence / Persona / Walkthrough with desktop+phone / Friction) + `screenshots/<tool>-desktop.png` and `-mobile.png` | — |
| `chart` | mindmap build-brief + Phase 0 | `reports/mindmap-pass/<DATE>-tool-usage.md` with all 12 build-brief columns, `lookup:` on every create row, every picked tool present; it runs `coverage_lookup.py` itself | code edits, page writing (`content_gen.py`) |
| `build` | Phases 1–8 | the site's real build exits 0 | — |
| `final` | build | `phase0-manifest.md` (Duplicate check passed), `audit.md` (auditor report naming every row, no FAIL verdict), standards-ledger phase-3/phase-5 entries, a `.meta.json` per new page, an inbound link to every new route, `phase8-summary.md`, ledger lines | `deploy-run-to-main.sh push` |
| `live` | deploy | every changed URL 200 with its `data-tool` root → writes `live.md` | the owner email |

Run dir = `reports/tool-usage-pass/<DATE>/`. Stamps (`*.ok`) and `/tmp/tool-usage-run.json` are written ONLY by the gate script; the hook blocks hand-made ones. A blocked call means: do the step it names. Never work around a block — there is no "small fix" exception.

**USER RULE — adds only.** The fleet is young. Low usage means "needs promotion or a fix", never "cut it". This routine never removes, merges, redirects, hides or deprioritizes a tool, a feature of a tool, or a page.

## STEP 1 — Pull this site's usage
```
python3 scripts/tool_usage/site_tool_usage.py --site "$TOOL_SITE" --days 30 > /tmp/tool-usage.json
```
Returns `{data_days, tools:[{tool, path, people, uses, views, use_rate, people_7d, lane}]}` from our own tracking table (non-bot only). `lane` is set by the script:
- `persona` — 3+ people used it → full persona pass (STEP 3 + STEP 4)
- `low-use` — 10+ views but under 25% of viewers touched it → persona pass focused on "why did they leave without using it" (STEP 3 only)
- `thin` — listed in the email, not worked

`error` in the output → STEP 8 email with `--status failure` (say what failed). No `persona`/`low-use` tools → STEP 8 email with `--status no-op` listing every tool and its numbers ("nothing crossed the bar this week"), then exit 0.

Otherwise open the run now: `python3 scripts/tool_usage/tool_usage_gate.py start --site "$TOOL_SITE" --base-url "$BASE_URL"`.

**Young-data rule.** `data_days` is how long this site has been tracked. Under ~30 days the numbers only decide WHICH tools to look at, never how big a change to make. Don't read meaning into rank order between tools 3 people apart.

## STEP 2 — Pick this week's tools
Ledger = `reports/tool-usage-pass/ledger.jsonl` (one JSON object per line, this repo). Skip any tool with a `worked` line in the last 28 days — UNLESS its `people_7d` is now at least double what the ledger recorded (it took off; look again).

Work up to **5 `persona` tools** (most people first) and **2 `low-use` tools** (most views first). The rest wait for next week.

Write them to `reports/tool-usage-pass/<DATE>/picked.json` — a list of the STEP 1 objects (`tool`, `path`, `people`, `lane`…).

## STEP 3 — Become the person using each tool (Lane A: fix what's in their way)
For each picked tool, in order:

1. **Evidence.** Collect, don't guess:
   - The page's top Google queries, last 28 days: `python3 .claude/tools/gsc-search-analytics/gsc_search_analytics.py --base-url "$BASE_URL" --page "$BASE_URL<path>"` (no GSC access → note it, use the page's H1/title/keyword instead). Queries are the closest thing we have to "what they came to do".
   - The tool's numbers from STEP 1 (people, uses, views, use_rate).
   - The tool's source (find the component that renders inside the `[data-tool="<tool>"]` root) and the live page.
2. **Persona card** (3 lines, grounded in the evidence): who they are + where they are (role, setting, device — e.g. "4th-grade teacher, laptop on a projector, class in the room"), the job they came to do (from the queries), and what "done" looks like for them (printed sheet, projected screen, a number to act on, a file).
3. **Do the job as them, on the live page.** Open `$BASE_URL<path>` in a headless browser at desktop (1366px) and phone (390px) widths and complete the job end to end with realistic inputs that persona would type. Browser setup in the cloud: `npm i --no-save --prefix /tmp/pw playwright-core playwright && npx --prefix /tmp/pw playwright install chromium` then drive it with a short script (`require('/tmp/pw/node_modules/playwright')`). The cloud image ships Chromium at `/opt/pw-browsers/chromium-*/chrome-linux/chrome` (pass it as `executablePath`). Save a full-page screenshot per width to `reports/tool-usage-pass/<DATE>/screenshots/<tool>-desktop.png` and `<tool>-mobile.png`. **Walk BEFORE you read or change the tool's code** — the walk is the evidence; the code is only for diagnosing what the walk found. No browser at all → stop the run and send a `--status failure` email saying so; never walk it "on paper".
   Record every point of friction, in the persona's voice:
   - a step that blocked or confused them; a label or output they wouldn't understand
   - an input they'd need that isn't there (their grade level, units, a second option…)
   - math/logic that is wrong, unexplained, or gives an answer they can't act on
   - no way to keep what they made (print, copy, download, fullscreen/project, share link) when their "done" needs one
   - phone layout breaks, controls too small, console errors, slow or broken load
   - `low-use` tools: what on the page, before the tool, would make them leave without trying it (tool below the fold, unclear first step, intimidating form)
4. **Write the persona file** `reports/tool-usage-pass/<DATE>/personas/<tool>.md` with exactly these sections: `## Evidence` (queries or "no GSC access", the STEP 1 numbers), `## Persona` (the card), `## Walkthrough` (what they did and saw at desktop 1366px AND phone 390px, step by step), `## Friction` (each item, or "none").
   After the last tool: `python3 scripts/tool_usage/tool_usage_gate.py persona`. Until it passes you cannot edit code.
5. **Turn each friction into a chart row** for the brief:
   - Tool behaviour/code → bucket `update existing body text`, **format `tool fix`**, target = the component file + route, solution = the exact change, problem = the persona quote + evidence.
   - Missing explanation/FAQ/how-to on the page → a normal `update existing body text` row (mindmap writes it via the API writer).
   - Nothing worth fixing → say so in the ledger and add the line `Walked, no friction: <tool>` under the chart table; that is a valid result (the `chart` gate checks every picked tool appears in the chart).

**Tool-fix guardrails** (the auditor fails any row that breaks one):
- Additive and bounded: never remove an existing input, output, mode, setting or feature; never change the URL, title, meta description or H1.
- The `data-tool="<slug>"` root stays exactly as it is (our usage tracking hangs off it).
- No new per-use paid API calls, no new runtime dependency over ~30 KB gz (the bundle gate will fail the build anyway).
- Math changes need a stated reason + a worked example in the row; if the right formula isn't certain, the fix is an explanation on the page, not new math.

## STEP 4 — What would they reach for next? (Lane B: new tools)
For each `persona` tool only: list the 2–3 jobs this same person does right before or right after this one (noise meter → a voice-level chart to print, a "quiet work" timer that ties to the meter; TSP withdrawal calculator → TSP vs IRA rollover comparison). Each becomes a `create new content` row, format `interactive tool` / `calculator` / `quiz/assessment`, with the seed tool + persona card as the `problem` evidence and what the tool DOES (inputs → outputs) in `solution`.

Client-side, deterministic tools only (no tool that costs us an API call per use). Do not dedup or validate here — mindmap's coverage lookup and demand ladder do that.

## STEP 5 — Run /mindmap-pass in full, unattended
Write the STEP 3 + STEP 4 rows, the persona cards and the usage numbers into one brief and run **`/mindmap-pass` in full** — every phase, in order, the same way the X-trends routine does. **Read each phase file; do not paraphrase.**

> Unattended run: save the chart to `reports/mindmap-pass/<YYYY-MM-DD>-tool-usage.md` (this exact name, so it never collides with another mindmap run today), treat the Phase 0 manifest as approved, and continue to Phase 9 without stopping.

**Every phase, in order, each phase file read before you act on it** — build-brief, 0, 1, 2, 3 (+3c), 4, 5, 6, 7, 7b, 8, 9. A phase with nothing to do still runs and says "nothing to do" in the Phase 8 summary. Files the gates check:
- after build-brief + Phase 0: save Phase 0's manifest table to `reports/tool-usage-pass/<DATE>/phase0-manifest.md`, then `tool_usage_gate.py chart`
- Phase 4: paste the independent auditor's full report to `reports/tool-usage-pass/<DATE>/audit.md`, ending with a line `VERDICT: PASS` (or `VERDICT: FAIL` — then fix and re-audit; the gate refuses a FAIL)
- Phase 8: save the summary to `reports/tool-usage-pass/<DATE>/phase8-summary.md`
- before Phase 9's deploy: `tool_usage_gate.py build`, then `tool_usage_gate.py final` (STEP 7's ledger lines must already be written)
- after Phase 9's deploy: `tool_usage_gate.py live`

Demand rule: a `tool fix` row is backed by real usage — volume never vetoes it. A new-tool row needs mindmap's normal demand read, but "a real user of the seed tool needs this next" is a valid signal when keyword tools return nothing; label it so.

### Tool rows: mindmap builds them (Phase 3c), this routine caps them at 3
mindmap's Phase 3 builds `interactive tool` / `calculator` / `quiz/assessment` rows for real via `phase-3c-tool-build.md`, and Phase 4 audits them with its tool checklist. **This routine's only addition: build at most 3 new tools per run** (by demand, then by seed-tool people). Give any extra tool rows a spec (`reports/mindmap-pass/specs/<slug>-spec.md`) and list them under "Next in line"; next week's run builds those first (the ledger's `spec` lines, STEP 2).

### `tool fix` rows — Phase 5 applies them, Phase 4's tool checklist audits them
Phase 5 routes `format: tool fix` rows to a code change in the named component (not the prose writer), then bumps the page's "last updated" date in the same change, per the Phase 4 editor rule. The same independent auditor checks every tool-fix diff against Phase 4's tool checklist plus: the diff only touches what the row says, and every STEP 3 guardrail holds. Fail → fix in place (2 tries), then drop that row.

Phases 6 (internal linking — every new tool gets a link FROM its seed tool's page, "next step" style, plus its hub), 7 (sitemap + IndexNow), 7b, 8 and 9 (commit → deploy → 200-verify → IndexNow) run unchanged.

## STEP 6 — Verify before you trust it
- The site's full build passes (Node 20).
- Every new and changed tool URL answers 200 live.
- Tracking still works on every new and changed tool: `PW_CORE=/tmp/pw/node_modules/playwright-core node scripts/tool_usage/verify_beacons.cjs "$BASE_URL" <path> [...]` → PASS (1 view + 1 use). No browser → `curl -s` the live page and confirm `data-tool="<slug>"` is in the HTML.
- Re-do the persona's job once on each fixed tool: the friction you fixed is gone.
- Any page that can't reach 200 after 2 fixes → revert it; never leave a 404 live.

## STEP 7 — Ledger
Append one line per tool to `reports/tool-usage-pass/ledger.jsonl` and commit it with the run:
`{"date","tool","lane","people","people_7d","views","use_rate","persona","findings":[...],"shipped":[...],"status":"worked"}`
and one `{"date","tool":"<new slug>","seed":"<tool>","status":"built"|"spec"|"dropped","reason"}` line per new-tool row.

## STEP 8 — Email the owner — EVERY run (USER RULE 2026-10-11)
Every run sends exactly one email through `.claude/scripts/send-routine-email.py`, the same script and layout as the other routines. Pick the status:
- `--status success` — something shipped. The hook blocks this until `tool_usage_gate.py live` has passed; use its `live.md` as the `## Live verification` section.
- `--status no-op` — the run worked but nothing changed (no tool crossed the bar, or every row was dropped). Still list the data and why nothing shipped.
- `--status failure` — a step or gate failed and could not be fixed. Name the step, the error, and what is left on the `claude/*` branch.

Write `/tmp/tool-usage-<YYYY-MM-DD>.md` first and pass it with `--details-file`. Written for a person reading their inbox. Sections, in order (skip a section only when it is empty, and say so in `## What changed`):

0. **`## Duplicate check`** — the Phase 0 manifest row (or "no new-page rows").
1. **`## What changed`** — 2–4 plain sentences: how many tools fixed, how many new tools, anything notable (a site-wide bug, a corrected figure). On a no-op/failure run, say why.
2. **`## Data`** — `<TOOL_SITE>, <data_days> days tracked. Worked: <tool> (<people> people), …`; note when `data_days` < 30 that the numbers are early.
3. **`## Fixes shipped`** — per tool: the persona in one line, then each fix as `- [<tool name>](<live url>) — <what changed> (why: "<persona quote>")`.
4. **`## New tools`** — `- [<name>](<live url>) — <what it does>. Next step after [<seed tool>](<url>).`
5. **`## Next in line`** — tool rows specced, not built this week.
6. **`## Dropped`** — every row mindmap or the auditor dropped, with the one-line reason.
7. **`## Live verification`** — the gate's `live.md` (HTTP status + tracking for every new and changed URL).

```bash
REPO="$(git remote get-url origin | sed -E 's#(git@github.com:|https://[^/]*/)##; s#\.git$##')"
.claude/scripts/send-routine-email.py --status <success|no-op|failure> --skill tool-usage-mindmap-auto \
  --site "$TOOL_SITE" --repo "$REPO" --branch main --commit-sha "$(git rev-parse HEAD)" \
  --summary "<N> tool fixes, <M> new tools from real tool usage." \
  --details-file /tmp/tool-usage-<YYYY-MM-DD>.md
```
A run that ends without sending this email is a failed run.
