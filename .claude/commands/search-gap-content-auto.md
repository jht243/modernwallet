# /search-gap-content-auto — user questions → live content

> **‼️ AUTONOMOUS.** No human checkpoint. Never print "Approve?". Auto-publishes to the live site. Nothing to write → exit 0 silently.

**The whole idea:** real people told us what they want. Turn that into pages. This is a thin wrapper around the mindmap engine — mindmap does the writing, auditing, and publishing. Do not build classification logic here.

## Project facts
- BASE_URL `https://www.themodernwallet.com` · repo `jht243/modernwallet` (Render autodeploys `main`) · search site key `themodernwallet.com`
- Content store: Astro content collections (Markdown files with frontmatter under `src/content/`) — Phase 0 of mindmap-pass discovers the exact page shape; template new pages into it exactly as this repo's `seo-gsc-pass/phase-3-new-content.md` does.
- Build gate: `npm run build (Node 20)`
- Deploy: `.claude/scripts/deploy-run-to-main.sh mark` at start, `push` at deploy (lands ONLY this run's commits on `main`)
- Search data comes from the shared fleet API (`growth-sites-api`) → Supabase `search_queries` rows with `site = themodernwallet.com`; the same rows feed the 8am "Site search" digest email for this site.

## STEP 1 — Get the questions
```
SEARCH_SITE=themodernwallet.com node scripts/search_gap_worker.mjs list-gaps --days 1 --limit 200
```
Returns `candidates: [{ term, kind, count, paths }]` — `kind:'search'` are zero-result nav searches (this site has no chat widget, so `kind:'chat'` will not appear). `paths` = the page they were on when they searched.

`candidateCount: 0` → exit 0 silently.

Requires `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`; missing → exit 0.

## STEP 2 — There is no STEP 2. Send it all.
**Do not filter. Do not classify. Do not judge. Do not skip.** The candidate list from STEP 1 goes into the brief whole, exactly as returned. Both streams. Junk, gibberish, probing, off-mission, things you are certain we already cover — all of it. Mindmap decides what becomes a page, what becomes an enrichment of the page in `paths`, and what gets dropped. That is its job and it is better at it than you are.

This routine has failed twice by pre-judging — once aliasing "already covered" terms, once ignoring "off-mission" ones — and both times real demand died before mindmap ever saw it while the run reported success. So there is no bucket, no filter, and no exception:

- **No aliasing.** `data/search-aliases.json` (if this repo has one) is not part of this routine. Do not open it.
- **No "already covered, no action."** A page existing while a real person still had to ask means that page failed them.
- **No off-mission or junk call.** Not yours to make.
- **No ignore list.** `data/search-gap-ignore.json` is no longer read or written by this routine. Do not add to it.

If the same term comes back tomorrow, it goes to mindmap again. Re-deciding a term costs one cheap dedup check; silently dropping a real question costs a page you never wrote.

## Not this routine's job — repo checklists
Do not add synthetic "we should also have X" rows to the brief (missing hub pages, series completeness, keyword wishlists). Those belong to the keyword/trend routines. On layer3 a checklist block once put 9 synthetic rows ahead of 20 real questions and consumed the run. The brief is what visitors searched for. Nothing else goes in it.

## STEP 3 — Feed them to mindmap
Write the surviving questions **and searches** into one brief and run the mindmap engine. **Read each phase file; do not paraphrase.**

- `.claude/commands/mindmap-pass/phase-build-brief.md` — brief = the raw terms, verbatim, one per line, each tagged with its `kind` and the `paths` page it came from. Force-create: a real person asked, so low search volume never vetoes it. SEMRUSH (optional) sharpens the angle only.
- `.claude/commands/mindmap-pass/phase-3-new-content.md` — write the pages
- `.claude/commands/mindmap-pass/phase-4-audit.md` — adversarial audit; hard-fail after 2 reworks → drop that topic and move on (do not record it anywhere; if it comes back tomorrow it gets another look)
- `.claude/commands/mindmap-pass/phase-7-sitemap-indexnow.md`
- `.claude/commands/mindmap-pass/phase-9-commit-deliver.md` — commit → deploy → 200-verify → IndexNow

**No cap. Work the entire brief.** Every candidate gets addressed in this run — there is no per-run page limit, no "roll to the next run", and no stopping early because the list is long. Mindmap's own dedup decides new-page-vs-existing; that is its job, not yours.

A run ends when the brief is empty, not when a counter is hit. If the brief is large, keep going.

**One rule mindmap does not know:** when `paths` shows the asker was already on a page that should have answered them, the fix is to **add the missing section to that page**, not publish a near-duplicate. Pass this to mindmap in the brief and let its dedup handle the rest.

## STEP 4 — Verify before you trust it
- The build gate above passes (this repo's `build` also runs `scripts/check-bundle-size.mjs` where present — a failure there is a real bug, not noise)
- **Confirm each new/edited page actually rendered** in the build output (or, for a server-rendered site, that its route answers 200 locally) before you push. A page that typechecks/builds but never appears is the classic silent failure.
- Every new page must appear in the sitemap AND in `search-index.json` on the next build (the index is baked from the same source at build time — if it is not there, the page is not reachable to the search box that asked for it).
- Any page that cannot reach 200 after 2 fixes → revert it, never leave a 404 live

## STEP 5 — Email the owner (only if something shipped)
Write `/tmp/search-gap-<YYYY-MM-DD>.md` with the sections below **before** you send the email, and pass it via `--details-file`. `send-routine-email.py` renders the markdown as the email body — write it for a human reading their inbox, not for a log.

**Required sections, in order:**

1. **`## New pages`** — every net-new URL published this run. One per line, as a markdown link. Example:
   ```
   - [<page title>](https://www.themodernwallet.com/<path>) — from "<the search term>" (search, /<page they were on>)
   ```
2. **`## Enrichments`** — every existing page you added a section to. Same shape, and name the section added.
3. **`## Dropped`** — every candidate mindmap discarded, with the one-line reason (duplicate of existing page, gibberish, prompt injection, out of scope, audit hard-failed twice, etc.). If the candidate list was 40 and you published 12 + enriched 6, the dropped section explains the other 22 — otherwise the report reads as if they vanished.
4. **`## Live verification`** — HTTP status for every new/enriched URL. Any non-200 is a run failure, not a footnote.

Do not summarize. Do not omit URLs "for brevity". Every URL that changed appears as a clickable link in this email — that is the whole point of the report.

```bash
REPO="$(git remote get-url origin | sed -E 's#(git@github.com:|https://[^/]*/)##; s#\.git$##')"
SHA="$(git rev-parse HEAD)"
NEW_COUNT=$(...)  # count of ## New pages entries
ENR_COUNT=$(...)  # count of ## Enrichments entries
.claude/scripts/send-routine-email.py --status success --skill search-gap-content-auto \
  --site themodernwallet.com --repo "$REPO" --branch main --commit-sha "$SHA" \
  --summary "${NEW_COUNT} new pages, ${ENR_COUNT} enrichments from user questions." \
  --details-file /tmp/search-gap-<YYYY-MM-DD>.md
```

Silent on empty runs (nothing published + nothing enriched → no email).

## Known limitation (context only — not a task for this routine)
The site search matcher ANDs every token, so multi-token phrases (`best mini pc budget`, `increase citations in llms`) return 0 even when a good page exists. That is a search-quality bug in the nav-search matcher, not this routine's. It is **not** your problem here and it is **not** a reason to skip a candidate — it just means some zero-result searches point at pages we already have. Send them to mindmap like everything else; mindmap will enrich the existing page rather than duplicate it.
