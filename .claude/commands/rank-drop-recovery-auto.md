## ‼️ THE DATA RULE — Google first-party only, hard fail otherwise

Every fact about **our site** in this run — which pages dropped, positions, impressions, clicks, sessions, recovery — comes from:

| Source | API | Used for |
|---|---|---|
| Google Search Console | `searchconsole.googleapis.com` (Search Analytics + URL Inspection) | rankings, queries, index status |
| Google Analytics 4 | `analyticsdata.googleapis.com` | organic landing-page sessions |
| Google Search Status Dashboard | `status.search.google.com/incidents.json` | is a ranking update rolling out |

**FORBIDDEN for any measurement of our site:** Ahrefs (MCP or API), SEMrush, DataForSEO (any endpoint), Similarweb, any estimate, any cached/older report, any number you "remember". There is **no fallback rung** — `_keyword-demand-ladder.md` does NOT apply to this routine.

**The one third-party exception (owner decision 2026-10-04):** DataForSEO may be called ONLY through `scripts/rank_drop/competitor_serp.py`, ONLY in Phase 2, and ONLY to list which OTHER sites now rank for a page's lost searches. The script takes those searches from the Google report, drops every row on our own domain before writing, calls no volume/keyword/difficulty/traffic endpoint, and writes a separate file stamped `third_party: dataforseo, purpose: competitor_discovery_only`. Nothing from that file may appear as a number about our site anywhere — not in detection, triage, the ledger, measurement, or the email's figures. Never call `scripts/lib/dataforseo.py`, `keyword_data.py` or `serp.py` directly in this routine.

**Hard-fail mechanics (not optional):**
1. `scripts/rank_drop/detect.py` must exit 0. Any non-zero exit (10 credentials · 11 auth/permission · 12 API error · 13 stale data · 14 empty data · 15 truncated data) = **HARD FAIL**.
2. `scripts/rank_drop/verify_provenance.py <detect.json>` must exit 0 **at the start of every later phase**. It rejects a report that is not OK, names any non-Google source, is older than 36h, or was edited after the pull (sha256). Exit 20 = **HARD FAIL**.
3. `scripts/rank_drop/measure.py` non-zero = **HARD FAIL**.
4. Every number in the email and the ledger must be traceable to `detect.json` / `measure.json`. Never type a position or click count yourself.

**On HARD FAIL:** do not edit any page, do not try another source, do not retry with a different tool. Commit nothing except (optionally) the FAIL report. Send the email with `--status failure`, headline `Rank-drop: HARD FAIL — Google data unavailable`, details = the FAIL `.md`. Exit.

## Site config — `scripts/rank_drop/site.json`

Every site value lives in `scripts/rank_drop/site.json` (base URL, GSC property, GA4 property, the
storage `backend`, price ledger if any, IndexNow key). Never type them into commands: the scripts read
the file. The engine is identical on every site; only the backend differs
(`backends/ts_entries.py` TS object literals · `py_registry.py` Python page dicts ·
`jinja_catalog.py` Jinja templates + catalogs · `pg_rows.py` Postgres rows).

| rule | value |
|---|---|
| Max pages fixed per run | **No cap** — every page that meets the drop rule and is not in cooldown |
| Meaningful-page floor | a page qualifies only if it averaged **≥ 1 Google click/day over the 90-day history** (`detect.py --min-page-clicks-d`, default 1.0) |
| Per-page cooldown | **28 days** from `treated` in the ledger |
| Price refresh (L2) | only when site.json has `price_ledger`; otherwise prices are checked by the auditor against the fact list |
| Ledger | `reports/rank-drop/ledger.jsonl` |
| Reports | `reports/rank-drop/<YYYY-MM-DD>.{json,md}` + `.measure.{json,md}` |

**Postgres sites (`"backend": "pg_rows"`, `"pg": {"apply_mode": "mcp"}`)** — the cloud runner cannot
reach the database directly; all row reads/writes go through the attached Supabase MCP connector
(`execute_sql`), scripted by `scripts/rank_drop/pg_mcp.py` (never hand-written SQL):
- before Phase 1: `pg_mcp.py select --detect reports/rank-drop/$D.json` → run the printed SQL with
  execute_sql → save the JSON rows to a file → `pg_mcp.py save --rows <file>`;
- edit steps (apply_sections / apply_fixes / rework / revert) only QUEUE guarded .sql files — nothing
  goes live before the audit;
- once, after the audit and before finish_run: `pg_mcp.py publish` → one small guarded UPDATE per page
  (`<page_key> <file>`); pass each file's contents to execute_sql exactly as written →
  `pg_mcp.py done --page '<page_key>' --result '<json>'`. `[]` = guard mismatch (row changed or a copy
  slip; md5 before+after guards mean a slip can only no-op): re-send once, then report it unpublished.
  A confirmation prompt or timeout = stop, leave the rest pending, report it;
- then `pg_mcp.py confirm` → run it → `pg_mcp.py save --rows <file>` (records the live rows).
Live pages are cached up to ~75 min after a write; finish_run's live check may time out on them —
that is reported, not a failure.

## Phase 0 — Detect + measure (Google only)

```bash
pip install -q google-auth requests   # cloud sandboxes don't ship them; a missing package is exit 10
python3 -c 'import json;[print(c) for c in json.load(open("scripts/rank_drop/site.json")).get("setup",[])]' | sh   # site-specific deps
D=$(date -u +%F)
python3 scripts/rank_drop/detect.py --out reports/rank-drop/$D || HARD_FAIL   # site.json supplies URL/GSC/GA4
python3 scripts/rank_drop/verify_provenance.py reports/rank-drop/$D.json || HARD_FAIL
python3 scripts/rank_drop/measure.py --ledger reports/rank-drop/ledger.jsonl \
  --out reports/rank-drop/$D.measure || HARD_FAIL
```

Read `reports/rank-drop/$D.md` and `$D.measure.md`.

**What "dropped" means here:** for every page×search, the last 14 days of finalized GSC data are compared against that pair's **best** 14-day position in the ~90 days before (its peak ranking, not its peak traffic — a news spike lifts traffic, not position). A loss counts when the pair ranked top-20 at its best, is now ≥5 positions worse, and is worse in both of the last two weeks. A pair still at its best position whose impressions fell is `DEMAND` (no action). `VANISHED` pairs are often searches about superseded models — Phase 1's Obsolete check routes those to REFRESH, not RECOVER.

**Measurement follow-through (do this before any new fix):** for every `WORSE` verdict, run `python3 scripts/rank_drop/revert_page.py --path <path> --sha <first sha in the ledger row> --date $D` (through the site's backend — never `git revert`, which cannot undo a database write and would undo other crons' later edits) and mark the ledger row `status: reverted`. `FINAL` rows (≥28d) get their verdict written into the ledger row. Reverts go through Phase 4 deploy like any other change.

**Owner override:** if the routine instructions contain the line `FORCE_FIX: yes`, add `--force-fix` to the detect.py call. The report then runs in FIX mode even during a Google update and records `mode_override`; the email headline must say `FIX (owner override during <update name>)`. Never add `--force-fix` on your own judgment.

**Mode gate:** if `detect.json` → `mode` is `OBSERVE` (a Google ranking update is still rolling out), **skip Phases 1–3 entirely**: no page edits while rankings are moving. Still run reverts above, commit the reports, then send the email EXACTLY as the Email section says (`email_report.py` builds the body even with no packets; append one `## Blocker` line naming the update). Never hand-write the email body. Rationale: fixes made mid-update chase a moving target and can't be measured.

## ‼️ NEW CONTENT = THE MINDMAP-PASS SYSTEM (owner rule, 2026-10-04)

Any reader-facing addition longer than ONE sentence — a section (L4), an FAQ answer, paragraphs, a
whole page (L5) — is produced by the same process mindmap-pass uses for new content: standards loaded
with `bash .claude/tools/load-standards.sh "rank-drop-recovery" "<phase>"` (git add the ledger),
`content_gen.py preflight`, a system.md per page type whose voice sample is a real sibling page that is
NOT being edited, DATA-ONLY prompts with the page's current text + closed fact list + closed URL list +
reader question/answer/placement, `content_gen.py section|write`, `.meta.json` committed, residue grep,
`scripts/content_lint.mts`, and the **mindmap-pass Phase 4 audit**. L4 = mindmap-pass **Phase 5**
(Enrichment chapter of `_content-generation.md`); L5 = mindmap-pass **Phase 3**.
**Exempt — written directly or by code:** titles/descriptions (L3), dates, price and number
corrections (L2), single fact-fix sentences, and one internal-link sentence (the L2 successor link).
That is the Enrichment chapter's own exemption list — nothing else is exempt.

## How this runs fast (the mindmap-pass model)

Work goes **phase by phase across ALL pages**, never page by page. Deterministic work is code;
judgment is batched across parallel planner/auditor subagents; prose is generated by parallel
content_gen API calls; one deploy at the end. (The first live run did one page end-to-end with
subagents and took ~22 min for 1 page — ~90% of it was rediscovery, a useless full-project `tsc`,
re-reading 124 KB of standards, and waiting on a deploy. Don't reintroduce any of that.)

**Parallel subagents:** launch a phase's subagents as several `Agent` calls in ONE message
(`run_in_background: false`) — that is blocking AND parallel. Never background them.
**No early stop:** work the whole queue. Only stop starting new pages if a phase errors out or the
session is genuinely near its context/time limit — elapsed time under 3 hours is NOT a reason.

## Phase 1 — Prepare + technical gate (FIX mode only; code, ~2 min)

```bash
P=reports/rank-drop/$D/packets
[ -f $P/queue.json ] && P=reports/rank-drop/$D-$(date -u +%H%M)/packets   # 2nd run today: own packets
python3 scripts/rank_drop/prepare_pages.py --detect reports/rank-drop/$D.json --out $P
GOOGLE_REPORTING_SA_JSON="…" python3 scripts/rank_drop/inspect_urls.py --packets $P
```
`prepare_pages.py` drops pages in their 28-day cooldown and UNSTABLE-only pages, and writes one
packet per page (entry location, headings, lost searches, lane hint, successor/taker routes, pricing
rows) plus shared `writer-rules.md`, `auditor-rules.md`, `routes.txt` and one system prompt per page
type. `inspect_urls.py` runs Google URL Inspection + a live fetch on every page; pages in
`tech.json` go to the **TECH lane** — fix the cause (canonical, noindex, redirect, 5xx) yourself,
commit, and remove them from the planner batches.

## Phase 1b — Diagnose every page on the escalating scale (code, <1 s)

```bash
python3 scripts/rank_drop/diagnose.py --packets $P        # writes <slug>/diagnosis.json + $P/diagnosis.md
```
Each page gets the LOWEST level that fixes it, plus any lower-level fixes it also needs:

| level | means | executor | cost |
|---|---|---|---|
| L0 MONITOR | page is net-healthy (clicks ≥ 90% of its 90-day average), or only junk/low-volume searches moved, or no gap | none — reported only | 0 |
| L1 TECH | URL Inspection / live fetch failed | you fix the cause (canonical, noindex, redirect, 5xx) | minutes |
| L2 DATA REFRESH | a priced model's "$X input … $Y output" disagrees with `data/pricing.ts`, or ≥50% of the lost demand was for an older model we already cover a successor of | `apply_data_refresh.py` — code only | seconds |
| L3 METADATA | the lost searches' words are missing from title/description, or another of our pages took them | planner writes one-sentence `meta` edits | ~10 s |
| L4 SECTION | the body doesn't answer lost searches, or the page is outranked on searches it already covers | planner (with competitor study) → one generated section | ~1–2 min |
| L5 REWRITE | most lost demand isn't served anywhere on the page | **the mindmap-pass new-content system** (Phase 3 Steps 0–3 + Phase 4 audit) applied to the existing route — `REWRITE_TASK.md` | ~3–5 min |

Do not escalate a page above its diagnosed level without writing the reason into its plan.

## Phase 1c — L2 data refresh (code, seconds)

```bash
python3 scripts/rank_drop/apply_data_refresh.py --packets $P --date $D
```
Fixes EVERY plain rate statement of a stale API price on the page (body, bullets, FAQ, table cells)
from `data/pricing.ts`, appends ONE internal-link sentence to the page lead pointing at our successor
pages (exempt — a new section would be new content), bumps
`updatedDate` — one commit per page. Sentences a number swap would break — comparisons ("cheaper",
"half the input cost", "doubles", "%"), worked examples ("$55 total ($25 … $30)"), price-history
narratives ("rises to $3 / $15" when the ledger says the increase was withdrawn), or an ambiguous
model name ("Sol" on a page that also names GPT-6 Sol) — are NOT touched; they are written to
`<slug>/fact-fixes.json` for Phase 1d. Never hand-edit a price.

## Phase 1d — Fact fixes (parallel fact-fix subagents, ~2 min)

For every page with a `fact-fixes.json`, launch fact-fix subagents in ONE message (batches of ~5
pages) with `scripts/rank_drop/FACT_FIX_TASK.md`. They write `<slug>/fact-edits.json` (exact old →
new sentence, derived figures recomputed from the ledger with the math shown). One-sentence
corrections are allowed in-context by the prose rule. `apply_sections.py` applies them in Phase 4 as
their own `FACT FIX` commit; the auditors check every number against the ledger.

## Phase 2 — Plan L3/L4 pages and rewrite L5 pages (parallel subagents, one message)

First, once for the run: `bash .claude/tools/load-standards.sh "rank-drop-recovery" "phase-2"` and
`python3 scripts/lib/content_gen.py preflight` (a failing preflight stops all L4/L5 work — never write the
prose by hand instead). Pages with diagnosis level **3 or 4** go to planners; level **5** pages go to
rewrite subagents. Launch both kinds together in ONE message.

**L5 = the mindmap-pass new-content system, not a separate one.** Rewrite subagents get
`scripts/rank_drop/REWRITE_TASK.md` (batches of ~4 pages): it runs `mindmap-pass/phase-3-new-content.md`
Steps 0–3 (standards loader + preflight, one system.md per page type with a sibling page as the voice
sample, DATA-ONLY row prompts with reader question/answer/placement and the PAA FAQ spec, `content_gen.py
write --schema guide|comparison`, guard check, topic-residue grep, template) and saves
`packets/<slug>/page.json`. The ONE exception to mindmap-pass's NET-NEW rule: the route exists and is
replaced in place (same slug/URL/publishedDate) by `apply_sections.py`.

L3/L4 planners: Split them into batches of ~10 and launch up to **6 planner subagents in one
message**. Each gets `scripts/rank_drop/PLANNER_TASK.md`, its slug list, `$P`, the detect.json
path, and the `DATAFORSEO_B64` key line (competitor discovery only, L4 only). Planners write
`plan.json` (+ `section.prompt.md` for L4, `page.prompt.md` for L5, and `allowed-urls.txt`) per page —
never data files, never prose. **L3 pages are `meta_only`** — no competitor study, no generation.
**L5 pages are `rewrite`** — a whole-page brief; slug, URL and publishedDate never change.

## Phase 3 — Generate (parallel API calls, ~8 min)

```bash
GEMINI_API_KEY=… scripts/rank_drop/generate_all.sh $P 6
```
Prose rule satisfied: every section (L4) and every regenerated page (L5, `content_gen write --schema
guide|comparison`) comes from content_gen with its `.meta.json`. Re-running `generate_all.sh` only
retries pages without output; a page that fails twice goes to `## Carried to next run`.

## Phase 4 — Splice + commit (code, ~1 min)

```bash
python3 scripts/rank_drop/apply_sections.py --packets $P --date $D
```
Lint runs in Phase 5 step 1 (`lint_new_text.py`, scoped to this run's text), never as a hand pass here.

Applies, per page and each as its own commit: the `FACT FIX` sentence edits, then the plan (L3 meta,
L4 section, or L5 `REWRITE` — the generated keys replace the old ones, everything the generator
doesn't produce such as slug, publishedDate, CTA and related links is kept byte-for-byte).
Syntax-checked with `syntax_check.mjs` (parse-only — never run the full-project `tsc`, it reports 16k
pre-existing errors). `applied.json` lists each commit.

**Testing the logic without touching pages:** add `--dry-run` to `apply_data_refresh.py` and
`apply_sections.py` — no data file is written; each page gets a `*.preview.diff` to review.

## Phase 5 — Audit + fix on the remediation ladder (parallel auditors, ~8 min)

**Load and apply `.claude/commands/_remediation-ladder.md` IN FULL.** A finding is fixed at the
cheapest rung that can fix it. Regenerating or reverting a section for a finding a reviewer could
have fixed with a replacement sentence is a failure of THIS phase (it cost the 2026-10-04 run 14 of
20 new sections).

**‼️ EVERY STEP BELOW IS A SCRIPT. Do nothing by hand** (owner rule, 2026-10-05): no hand-built
commit lists, no ad-hoc Python splices, no hand-typed ledger rows, no hand-run lint triage. If a
script fails, fix the script and re-run it; never route around it in the terminal.

1. **Rung 0 — scoped lint:** `python3 scripts/rank_drop/lint_new_text.py --packets $P` → each page's
   `lint.json` holds ONLY the FAILs the run's own commits introduced (content_lint filtered to the
   added text; gear deep-dives / open-weights pages checked directly). Text already on the page before
   the run is never in scope.
2. **Batches:** `python3 scripts/rank_drop/audit_batches.py --packets $P` → prints one brief per batch
   (`$P/audit-batch-<n>.md`: pages, commits, standard, RUNG 0 items).
3. **Audit (parallel, ONE message):** one auditor per brief, prompt exactly
   `Follow scripts/rank_drop/AUDITOR_TASK.md for <brief path>. Date dir <date dir>.` Each writes
   `<slug>/audit.json` (`mechanical` / `fixes` as exact old→new, `rework`). Keep every auditor's id.
4. **Rung 1 — FIX-IN-PLACE:** `python3 scripts/rank_drop/apply_fixes.py --packets $P --date $D` applies
   every pair verbatim (one `AUDIT FIX` commit per page) and writes `$P/recheck.json`. Send each
   batch's SAME auditor (SendMessage) `Re-check per AUDITOR_TASK.md § Re-check, batch <n>, $P/recheck.json.`
   Where SendMessage is not available (cloud routines have only Task), launch one fresh auditor per
   batch with that same one-line prompt: the § Re-check protocol is self-contained (it reads only the
   AUDIT FIX diff), so no context is lost.
   Repeat 4 until recheck.json is empty or only `rework` remains (apply_fixes never re-applies a round).
5. **Rung 2 — REWORK, only for substance:** `python3 scripts/rank_drop/rework.py --packets $P --date $D`
   archives the failed draft, appends the CORRECTIONS block (auditor findings + current ledger rows
   for every model family on the page) and lists the page in `rework.json`; a page past its 2nd
   rework has its entry restored to the run base (`REVERT` commit) and goes to Flagged. Then:
   `scripts/rank_drop/generate_all.sh $P` → `python3 scripts/rank_drop/apply_sections.py --packets $P
   --date $D --rework` (replaces the section in place, meta untouched) → back to step 1 for those
   pages, and their auditor audits them FULLY. If `apply_sections --rework` reports a `REWORK:` guard
   error, run `rework.py` again: it turns the guard error into the next CORRECTIONS block (still
   counted against the cap of 2). Never soften an auditor's instructions (no "PASS on nits").
   `out_of_scope` findings (pre-existing text) never fail a page; list them under Flagged in the email
   from `finish.json`.
6. **Scope is the data diff only.** Packet/report files are artifacts; commits stage only `data/` +
   that slug's packet dir.

## Phase 6 — Deploy once, verify, ledger, email

1. `.claude/scripts/deploy-run-to-main.sh push` (all passed commits at once).
2. `python3 scripts/rank_drop/finish_run.py --packets $P --date $D` — ledger row per PASSED,
   un-reverted page (targets copied from packet.json's Google pairs), live check (200 + the new
   section heading as it now reads in data/, 15-min cap), ONE IndexNow POST for the live URLs,
   commits the packets + ledger. Its `finish.json` feeds the email.
3. `.claude/scripts/deploy-run-to-main.sh push` again (the packets/ledger commit), then email.

stops early (hard fail, OBSERVE), still run it: it prints "No pages needed changes" and you add the
blocker as one `## Blocker` line appended to the file before sending.
