# Audit the complete rendered page

This contract applies to every routine that creates or changes website content, metadata, templates, injected sections, dates, internal links or structured data. It applies equally to local, global and cloud execution. It strengthens the existing independent audit and publication gates; it adds no phase or human approval.

## Prepare the answer before the approval chart

Finish research needed for the proposed answer, setup instructions, pricing, product availability, comparisons and takeaway before marking preparation Passed. “Fetch/verify in Phase 3” is unfinished preparation when the source supports the proposed answer. Optional unsupported material must be explicitly excluded from the approved scope, not presented as planned content with a future verification condition. Missing paid metrics may retain the authorized labeled fallback. Keep one preparation summary row and every complete new-page brief.

## Define the actual affected scope

Record every changed route and all routes affected by a shared template/helper, including affiliate, related-content, survey, attribution and date transformations. Enumerate these through the site's route registry or build output. A shared change is not confined to the example page that exposed it. Preserve unrelated content, exclusions, professional review and the existing no-addition branch. If a shared change affects a large set, mechanically inspect every affected route and independently review every distinct changed copy/template variant plus its source-support mapping. Record the complete route inventory and justify representative visual samples; never call a sample a full route check.

Prepare a JSON manifest with `author`, `canonicalBase`, and a nonempty `routes` array. Each route has `path`, optional `expectedUpdatedDate`, required on-page `requiredText` where useful, `forbiddenText` for the defects being repaired, and optional `growthFile`/`evidenceFile`. Use actual source dates rather than today's date for untouched pages. A route expected to carry an updated date must set `expectedUpdatedDate`; document genuine date-policy exceptions in the independent review.

## Existing Phase 4 audits the final candidate

1. Apply planned content, link edits and all reader-facing transformations before the final approval of affected pages. Monetization is content: an “append-only” map entry can add unreviewed prose and regress dates. Build/export or serve the candidate through the production rendering path. Never substitute a raw data object, generator draft or source grep for the rendered page.
2. Capture each complete rendered page with `.claude/tools/rendered-audit.py capture --manifest MANIFEST --base-url PREVIEW_OR_LIVE_BASE --out SNAPSHOT.json`. The helper saves HTML and readable text, metadata, links, structured data, dates and a semantic fingerprint. Static/server-rendered pages can use their complete HTTP HTML. For client-rendered pages, save the hydrated browser DOM to a directory named by route (`index.html` for `/`, otherwise `path/index.html`) and pass `--dom-dir`; also inspect the page in the browser. An empty app shell is not a page capture. Capture delivery must be complete: if the browser API caps long strings, return bounded chunks from one DOM snapshot together with its full length, join them outside the browser, and verify the returned length. Require actual parsed body and HTML closures; a truncation marker or a closing-tag string inside a script/comment does not prove completeness. Retain the complete raw HTML. Inspect responsive layout, tables and interactive behavior in the browser where applicable; record actual observations and evidence.
   Rotating third-party ads may use the helper's narrowly identified `volatileThirdPartyAds: "mediavine"` route option only when the independent review explicitly covers that normalization. The manifest binds the option to the review. Retain raw HTML and inspect real ad placement/overlap in browser evidence. Never exclude generic ad-like wrappers or first-party article text, reader-survey results, affiliate content, tested labels, bylines or structured data. Protected content inside an excluded region, an unverified wrapper or an unterminated region blocks capture. All other semantic content remains exact.
3. An independent reviewer who did not write the changes must read the entire rendered decision path, including inherited paragraphs, tables, FAQs, conclusions, injected copy, footer/disclaimers and visible labels. Contradictory or unsupported material affecting the revised answer is a blocker even when it predates the run. Unrelated historical style issues may remain advisory. Do not rewrite unrelated pages to satisfy a quota.
4. Audit all existing content/evidence/testing rules against the render. A vendor name or generic template cannot establish availability of an exact model in an editor, product integration, first-party app or paid plan. Verify the exact combination with a primary source or use useful conditional language with a direct availability link. Preserve relevant monetization and disclosures without claiming unsupported compatibility or popularity.
5. Verify the rendered visible updated date, pricing/disclaimer dates and JSON-LD against the intended source date. `dateModified` must never precede `datePublished`; injected content must never replace a newer date with an older constant. Sitemap lastmod follows the existing substantive-change policy; document legitimate link-only differences rather than stamping every page.
6. The reviewer saves a JSON review with `reviewer` (distinct from manifest `author`), `snapshotSha256`, and one result for every route: `fingerprint`, `verdict: PASS`, and evidence-backed `checks` for `wholePageCoherence`, `sourceSupport`, `testingAndAttribution`, `datesAndSchema`, `linksAndIndexability`, `renderedLayout`, and `scopeAndExclusions`. Each check is `{status: PASS|NA, evidence: concrete observation/artifact}`. NA needs a specific reason; the whole-page, source, date/schema, links and layout checks cannot be NA. The helper validates records, not reviewer understanding or factual truth. Never generate a review by filling PASS defaults.
7. Run `rendered-audit.py check --snapshot SNAPSHOT.json --review REVIEW.json --recapture`. Recapture uses the same actual preview/live origin and compares the current rendered fingerprints with the approved ones. For hydrated DOM, refresh the browser capture first; the independent reviewer must verify its freshness. A changed fingerprint, missing route/check, mechanical failure or same author/reviewer blocks publication. Every content/template/affiliate change after approval invalidates the affected page approval and requires recapture and independent review. Do not count a content rewrite as already approved because the underlying source record passed earlier.

## Existing publication gate verifies the live render

After the host deploys the intended revision, capture every affected live route and run `rendered-audit.py compare --approved PREVIEW_SNAPSHOT.json --live LIVE_SNAPSHOT.json --review REVIEW.json`. The complete semantic render must match the approved candidate; build IDs, script payloads and preview-origin URLs are excluded, but visible copy, metadata, links and JSON-LD are not. If rendering legitimately differs, independently review the live difference and correct the candidate; HTTP 200 alone is not success. Check actual host deployment evidence and preserve it with the commit ID. Submit IndexNow only for eligible verified live URLs under existing rules.

Close the measurement handoff with `rendered-audit.py record-deployment --snapshot LIVE_SNAPSHOT.json --approved PREVIEW_SNAPSHOT.json --review REVIEW.json --commit VERIFIED_COMMIT --deployment-evidence HOST_EVIDENCE.json --ledger reports/content-evidence.jsonl`. The host evidence must identify that commit and a successful live deployment. This updates manifest-linked growth records, recording the live verification, commit, evidence paths, baseline availability and first complete 28/56-day windows.
